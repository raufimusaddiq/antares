# Research: Anti-Slop Writing Rules

**R1 - Delivery: run instructions, not a Hermes skill.** Decision: the rules are sent as `instructions` on every run (chat and post check), as the personal instructions and the OpenUI instruction already are. Rationale: it reaches every existing and future account at once with no profile change; the constitution forbids Antares writing into Hermes data directories beyond profile create/delete, so a skill folder per profile is out; and Hermes' skill loader decides by itself when to load a skill, which would make "always apply" unreliable. Alternatives: a Hermes skill installed in each profile (rejected: boundary, backfill for existing profiles, no admin switch); a model-side system prompt change in Hermes (not Antares' to change).

**R2 - What is built in (Q1).** Decision: only the writing and copy rules of the upstream skill, condensed to ~2.3k characters (see contracts/rules-text.md): em dashes, the banned buzzword and filler lists, significance inflation, authority tropes, announcing openers and theatrical closers, negative parallelism, forced trios, formatting tells, fabrication (numbers, quotes, testimonials, certifications), generic calls to action. Source files read: `skills/antislop-copywriting/SKILL.md` and `skills/antislop/SKILL.md` rules R-02, R-15, R-16, R-17, R-18, R-36 (upstream has no VERSION file for the copywriting skill, so the version is ours: `writing-rules v1`, and the upstream commit is recorded in the runbook). Licence: MIT, "Copyright (c) 2026 Miqdad Badjuber (antislop)", kept in the text's header line and in the runbook. Alternatives: the whole 54k-character core skill (rejected: ~13k tokens per run, mostly UI rules).

**R3 - When it applies (Q2).** Decision: the text itself says the rules apply only to prose written for the person to use, never to answers, explanations, code, tables or quotations, and that a person's own tone request wins except for invented facts. The model decides, as with any instruction; the rules text also tells it to explain the rules plainly when asked and to follow a requested tone except for invented facts (both checked in the quality run); the test is the fixed prompt set (SC-001, SC-003), run for real on production. Alternatives: Antares classifying each message (rejected: a second pipeline, Principle II).

**R4 - Order with the personal instructions (FR-005).** Decision: rules first, personality after, so the later, more specific instruction wins on tone; the rules text says the person's instructions win except for inventing facts. Alternative: personality first (rejected: the model weights the last instruction most; the person's tone must win).

**R5 - Post assistant (Q-style note).** Decision: add the rules to the check prompt (`blog-check v2`) and a note kind `style` to the existing envelope; notes remain plain text, anchored after a node, at most the existing limit; the browser lists them with the other notes, each dismissible (browser state, not stored: the notes belong to one check result the author is reading). A style note never blocks publishing (the publish flow does not read notes today). Alternatives: inline highlights (rejected by the owner, Q1 answer A).

**R6 - Summaries (FR-006).** Decision: replace `summaryStyle` with the shared text through a hook on the helper (like the model Pick of spec 004), so summaries cannot drift from chat. Titles stay as they are (a title is not prose the person writes with it).

**R7 - The switch.** Decision: one row `writing_rules_setting(enabled, updated_by, updated_at)`, absent row = on. Admin-only (Q3 answer), audited as `writing_rules.set`. Read once per run. A read error applies the rules (fail to the safer, documented default) and logs.

**R8 - Seeing "not applied" (FR-009).** Decision: each run and each check records what happened to the rules: the version (`v1`), `off` (the administrator had them switched off) or NULL (they should have been attached and were not). The admin card shows, for the last 24 hours, counts with the rules (`v1`) and without (`off` and NULL together); the warning appears only for NULL on runs started since migration `0029` was applied (`schema_migrations.applied_at`), so runs that predate the feature, and runs while the rules were switched off on purpose, never raise it. Aggregate only: no user, chat or post identifier; titles and summaries are not recorded, so the counts say "chat and post-check runs". Alternative: a log line only (rejected: the administrator would not see it).

**R9 - Size (SC-007).** Decision: cap the text at 3,000 characters, enforced by a test; the measured size goes into `validation.md`. At about 750 tokens it is smaller than the OpenUI instruction already sent.

**R10 - Quality measurement (SC-001, SC-003, SC-004).** Decision: a fixed prompt set (20 writing, 10 non-writing, 3 drafts) run by a throwaway script against production with synthetic accounts, with and without the rules (the administrator switch makes the baseline possible), counting em dashes, banned words and numbers without a source with regular expressions; results in `validation.md`. The script is not committed (AGENTS.md: no measuring code). Limitation: it measures a model, so it is evidence, not a guarantee.
